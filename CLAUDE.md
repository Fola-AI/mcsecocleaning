Read at the start of every session. These rules hold across every stage. Where a rule and a convenience conflict, the rule wins. `AGENTS.md` (imported above) is maintained by `next dev` — keep it; it warns that Next.js 16 differs from your training data, so read `node_modules/next/dist/docs/` before using a framework API you're unsure of.

## The project in one paragraph

mcsecocleaning is a UK eco-friendly cleaning company's web platform: a local-SEO marketing site, an instant-quote booking and payments system, an operations back office with a crew mobile interface, and a customer portal. South London launch (§4 of PRD). Next.js 16 App Router + React 19 + TypeScript + Tailwind v4 on Vercel (`lhr1`), Neon Postgres via Prisma 6, Auth.js (next-auth v5), Stripe, Inngest, Resend, R2, Twilio. Phases 1–2 are built; you are building the rest as stages L1–L15.

## The loop (every unit of work)

1. **Read** — `PROGRESS.md` (current stage, next action, open items), the stage in PRD §16.3, every PRD section it references, and the code you will touch.
2. **Plan** — write the stage plan as a checklist under the stage in `PROGRESS.md` before coding. Name files, schema changes, tests.
3. **Build** — small steps. Tests alongside code, not after.
4. **Verify** — run the gate (below). Red means fix, not skip.
5. **Review** — self-review the diff against the checklist below. For diffs touching pricing, payments, auth/RBAC, access codes or migrations, do a second, fresh-context review pass (a subagent if available) before committing.
6. **Update `PROGRESS.md`** — ticks, real command output as evidence, decisions logged, review-queue entries, next action.
7. **Commit** — one logical unit per commit, conventional message (`feat(l4): slot availability service`), `PROGRESS.md` updated in the same or the immediately following commit. Push `build/autonomous`.
8. **Next** — next item, or next stage once every acceptance criterion has evidence.

### The verify gate

```
npm run typecheck        # tsc --noEmit
npm run lint             # eslint
npm test                 # node --test via tsx, src/**/*.test.ts
npm run build            # prisma generate + price parity check + next build
npm run test:e2e         # added in L2; run for anything the stage touches
npx prisma migrate diff --from-url "$DIRECT_URL" --to-schema-datamodel prisma/schema.prisma --script   # after any schema change — must print an empty migration
```

Paste real output. Never write "tests pass" without the output.

### Self-review checklist

- RBAC: `requireRole` on every new route/action; ownership filter on every customer-scoped query; crew sees only assigned jobs.
- No secret reachable from the client: nothing sensitive prefixed `NEXT_PUBLIC_`; server modules import `server-only`.
- Money: integer pence; net / VAT / gross stored; consumer display VAT-inclusive; every price read from the rate card.
- Time: stored UTC, rendered Europe/London; BST/GMT considered.
- Idempotency on anything a webhook or cron can repeat.
- No access code in any log, email, SMS, error or analytics payload.
- UK English and UK terminology in code, copy and URLs.
- Tests cover the failure paths, not just the happy path.

## Decision boundary

### Decide it yourself and log it
Implementation choices inside the locked stack; libraries for tests and tooling; file structure; refactors; component design; UI layout and copy that makes no factual claim about the business; test design; additive schema changes (new tables, new nullable columns, new enum values); dev-only defaults. Log each non-trivial one in `PROGRESS.md` → *Decisions made* (what, why, alternative considered, how to reverse).

### Park it and keep going
Write it in `PROGRESS.md` → *Open questions for Fola*, give the options (do not pick one), then continue with other work. If the stage can't finish without the answer, mark that item Blocked and move to the next stage whose dependencies are met.
- Any product or business decision the PRD doesn't settle.
- Any change to rate-card **figures**, fees, discounts, deposit thresholds or remedy windows.
- Copy that states a fact about the business (insurance, DBS, years trading, products used, company details, guarantees). Use the repo's markers instead — `TODO(business-input)`, `TODO(pricing)`, `TODO(legal)`, `TODO(ops)`, or a `PLACEHOLDER` value in `src/config/*` — never invent the fact.
- Legal wording (T&Cs, privacy, cancellation, CCR consent text changes).
- A PRD contradiction you can't resolve from §17.
- Missing keys for a stage.

### Review queue (non-blocking)
These you build, test and commit, then list under *Review queue* in `PROGRESS.md` with the file path and a two-line summary. Fola reviews them at merge checkpoints. Per SETUP decision D1 — if Fola chose "stop on every migration", schema changes move to Hard stop.
- Every new manual migration (SQL file + `schema.prisma` diff).
- Any change to pricing logic (`src/lib/pricing`), payment flow (`src/lib/stripe`, webhooks), auth/RBAC, or access-code handling.
- Any destructive schema change (drop, rename, type change, NOT NULL on an existing column) — additionally write the data-safety reasoning.

### Hard stop — stop the session and flag Fola
Write the reason at the top of `PROGRESS.md` under **⛔ STOPPED**, commit, and end.
- Anything that would touch production: the Neon `production` branch, Vercel production env or deploys, live Stripe keys, DNS, the live domain.
- A secret found committed to the repo or printed somewhere it shouldn't be.
- The same verify-gate failure after three genuine fix attempts.
- Anything that spends money (plan upgrades, paid add-ons, buying a number).
- Sending real email/SMS to anyone other than the dev redirect addresses.
- Deleting data anywhere except the `dev` database.
- A PRD MUST that is impossible as written.

## Git and environments

- Work on `build/autonomous` (L1 creates it). Push it freely — it deploys as a Vercel preview.
- **Never push to, merge into, rebase or force-push `main`.** Fola merges at the checkpoints in PRD §16.2.
- Never `git push --force` anything. Never rewrite pushed history.
- The only database you touch is Neon `dev`. Every migrate/reset/seed runs through `scripts/assert-dev-db.ts` (built in L1), which refuses unless the host equals `DEV_DB_HOST`.
- Manual migrations: `prisma/manual-migrations/YYYY-MM-DD-name.sql`, idempotent where possible (`IF NOT EXISTS`), applied to `dev` with `psql -v ON_ERROR_STOP=1`, followed by the empty drift check. Never hand-fix a row to get past a failure.
- **Merge checkpoints** (PRD §16.2): when a checkpoint stage passes, write *Checkpoint N merge notes* in `PROGRESS.md` — the migrations Fola must apply, in order, to whatever database Vercel Production points at *before* merging (migrate-before-swap); new Production env var names; review-queue items in scope; a ready-to-paste PR description. Then carry on with the next stage on the same branch.
- Stripe: test mode only (`sk_test_`/`pk_test_`). Any `sk_live_` in the environment is a Hard stop.
- Outbound comms: when `APP_ENV !== "production"`, email goes to `DEV_EMAIL_REDIRECT` and SMS to the log or `DEV_SMS_REDIRECT`. The guard is tested; never bypass it.

## Security rules

- Secrets live only in `.env.local` (git-ignored). Never print, echo, log or paste a key value — refer to keys by name.
- Server-only secrets never get a `NEXT_PUBLIC_` prefix and never cross into a client component.
- Authorisation is server-side on every route, server action and query. Hidden UI is not access control.
- Access codes: encrypted at rest with `ACCESS_CODE_ENC_KEY`, revealed only to the assigned crew inside the time window, every reveal and refusal logged, never in any message body. The future agent never receives them.
- Rate-limit quote, booking, auth and crew-PIN endpoints (L14 at the latest).
- Webhooks verify signatures and are idempotent on event id.

## Money rules

- Prices come from the deterministic rules engine and the versioned rate card. Never from a model, never hardcoded. Any new price surface joins the parity gate in the same commit.
- Store net, VAT rate, VAT amount, gross. Consumer display is VAT-inclusive, total including all mandatory charges. Never "£X + VAT" to a domestic customer.
- Schedule ≠ billing. Payments never create, delete or move jobs; a failed payment flags, it doesn't remove.
- Existing quotes and subscriptions are never repriced by a code or card change.

## Content and compliance rules

- **Business facts from config only.** Trading name, company number, registered address, phone, NAP, trust facts and social links come from `src/config/site.ts`; services, areas, payments policy, discounts, checklists and legal wording from the other `src/config/*` modules; money from `src/lib/money.ts`; prices from `src/lib/pricing/rate-card.ts`. Never hardcode them in pages, emails or schema markup — NAP must match Google Business Profile character for character.
- **No invented reviews, ratings, counts or statistics.** Reviews render only from real `Review` rows; the social-proof strip needs ≥10; the trust-metrics bar stays out of the layout. No sample data in components, not commented out, not behind a flag. Seed data lives only in the seed script and is never rendered on public routes in production.
- **Banned claims and terms:**
  - "deposit back guaranteed" or any promise of a deposit, landlord, inventory-clerk or insurer outcome — we promise the **re-clean guarantee** only
  - "professional cleaning is legally required" (Tenant Fees Act 2019)
  - "Google Guaranteed", "DBS-checked", "fully insured", "eco-certified", "£5m cover", "years trading", "No.1", "best in London" — unless the fact is confirmed by Fola in `src/config/site.ts` (a `PLACEHOLDER` value is not confirmation)
  - "+ VAT" on any consumer-facing price
  - US terms: maid, residential cleaning, move-out cleaning, post-construction, ZIP code, sq ft for domestic
  - "cash" as a payment method
- **UK terminology:** domestic cleaning, end of tenancy cleaning, deep cleaning, after builders cleaning, communal area cleaning, postcode.
- **Reviews law (DMCC 2024):** no review gate; everyone gets the public request; incentivised reviews carry provenance and disclosure.
- **PECR:** marketing gated on consent; unsubscribe and SMS `STOP` honoured across channels.
- **Location pages:** district level only, publish gate (≥400 area-specific words, ≥1 area photo, ≥1 area review, area notes) enforced in code.
- **CCR consent** checkbox wording is versioned; changing it is a Park item.

## Code conventions

- Server components by default; `"use client"` only where interactivity needs it.
- `params` and `searchParams` are Promises in Next 16 — `await` them.
- Server actions in `src/app/actions/*`; anything exporting non-async helpers lives in `src/lib/*` (a `"use server"` file may only export async functions).
- Guard DB access with `hasDatabase` the way existing code does, so pages still render without a database.
- Code comments cite PRD v2.0 section numbers; PRD §17.6 maps them. New comments cite current `PRD.md` numbers.
- TypeScript strict. UK English in identifiers, copy and comments.
- Integer pence for money; `Date` in UTC; render with Europe/London.
- Pure logic in `src/lib/*` with unit tests; server actions thin.
- Accessibility WCAG 2.2 AA; mobile-first; `next/image` for every image.
- No new dependency without a one-line justification in *Decisions made*.

## Session protocol

**Start:** read this file → `PROGRESS.md` (if **⛔ STOPPED** is present and unresolved, stop and say so) → the current stage in PRD §16.3 → `SETUP.md` Decisions → `git status` and `git log -10` to confirm the tree matches *Next action*. Check `.env.local` has the keys the stage needs (names only).

**During:** update `PROGRESS.md` after every completed item, not at the end. A crash must never lose more than one item of work.

**End:** `PROGRESS.md` shows the exact next action, all work committed and pushed to `build/autonomous`, nothing left uncommitted.

**Context:** prefer reading the PRD section a stage cites over the whole PRD. Keep `PROGRESS.md` evidence trimmed to the decisive lines of output.
